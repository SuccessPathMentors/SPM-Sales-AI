# CR-107-02 — Authoritative Acceptance Evidence Fail-Closed

Status: DEPLOYED / VERIFIED — CLOSED
Work Unit: WU-107
Trigger: RT-107-12 internal executable runtime-path certification
Upstream release: CR-107-01

## Blocking finding
The exact Code-node runtime harness proved a P0 truth inconsistency in `Apply WU107 Existing Handoff Result`.

Fixture:
- persisted record label: `handoff_state=ACCEPTED`;
- queue receipt evidence: present;
- authoritative human acceptance evidence: **absent** (`downstream_acceptance_present=false`).

Observed before CR-107-02:
- customer-facing wording did not falsely claim that a person accepted the case;
- `human_acceptance_verified=false`;
- **but internal `handoff_state` remained `ACCEPTED` and `success=true`**.

This violates the WU-107 truth contract: `ACCEPTED` is a derived truth state that requires authoritative acceptance evidence, not a trusted label from persisted data.

## Root cause
The existing-result node calculated an `accepted` boolean correctly, but then constructed execution truth using the raw persisted `state`:
- result state: `accepted ? 'ACCEPTED' : state`;
- success: raw state membership in `QUEUED|ACCEPTED`;
- fail-closed: raw state membership in `QUEUED|ACCEPTED`.

Therefore an inconsistent persisted record could retain successful `ACCEPTED` execution truth even though the evidence gate failed.

## Fix
Change only `Apply WU107 Existing Handoff Result` so that it derives an **effective truth state** from evidence:

- `ACCEPTED` only when:
  - persisted state is `ACCEPTED`;
  - durable queue receipt is present;
  - authoritative downstream acceptance evidence is present.
- `QUEUED` only when:
  - persisted state is `QUEUED`;
  - durable queue receipt is present.
- inconsistent `ACCEPTED` or `QUEUED` labels without required evidence => `FAILED`, `success=false`, `fail_closed=true`.
- `human_acceptance_verified` remains false unless all acceptance conditions are proven.
