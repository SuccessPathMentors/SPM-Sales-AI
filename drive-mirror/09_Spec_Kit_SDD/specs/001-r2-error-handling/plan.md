# 001 R2 Error Handling — Technical Plan

Status: Ready for candidate implementation
Date: 2026-08-20
Parent spec: 001 R2 Error Handling

## 1. Objective
Add explicit, observable, bounded failure handling around the validated human-handoff Google Sheets lookup and append-or-update operations while preserving every locked R1 behavior.

## 2. Baselines
- Behavioral baseline: ChatBotMSE_v2_R1_LOCKED_2026-08-17.json.
- Latest Drive main-workflow checkpoint: ChatBotMSE_v2_R2_TOKEN_OPTIMIZED_2026-08-18.json.
- Candidate implementation base: Validated_Human_Handoff_FIXED.json.
- Permanent R1 regression suite: 10/10 cases in QA_TESTING_RELEASE_GATE.md.

## 3. Current Architecture Finding
The main workflow remains model-mediated for final submission: Route Sales Decision → AI Agent, with Submit Validated Human Handoff attached as ai_tool. The validated subworkflow already owns deterministic validation, duplicate/session checks, and append-or-update. This feature will harden that subworkflow rather than redesign the main state model.

## 4. Affected Nodes
Existing nodes to modify:
1. Check Existing Lead Record.
2. Upsert Validated Human Handoff.

New nodes:
3. Return Lead Lookup Error.
4. Return Lead Write Error.

Unchanged protected nodes:
- Validate Lead Payload.
- Is Lead Payload Valid?.
- Return Lead Validation Error.
- Assess Existing Lead.
- Is Lead Record Safe?.
- Return Lead Conflict.
- Return Handoff Success.
- All main-workflow nodes, including AI Agent and Submit Validated Human Handoff.

## 5. Implementation Design
### 5.1 Lookup reliability
Configure Check Existing Lead Record with bounded retry: retryOnFail=true, maxTries=2, waitBetweenTries=1000 ms. Configure node error behavior to produce an explicit error output rather than terminating without a structured result.

Success output continues to Assess Existing Lead exactly as today.

Error output routes to Return Lead Lookup Error.

Return Lead Lookup Error returns a minimal structured object:
- success=false
- status=lookup_failed
- error_code=LEAD_LOOKUP_FAILED
- safe multilingual user messages

No stack trace, credentials, internal sheet identifiers, or raw provider error is returned to the user-facing payload.

### 5.2 Write reliability
Configure Upsert Validated Human Handoff with bounded retry: retryOnFail=true, maxTries=2, waitBetweenTries=1000 ms. Use an explicit error output.

Success output continues to Return Handoff Success exactly as today.

Error output routes to Return Lead Write Error.

Return Lead Write Error returns:
- success=false
- status=write_failed
- error_code=LEAD_UPSERT_FAILED
- safe multilingual user messages

No success message can be generated by the subworkflow when this branch executes.

### 5.3 Idempotency
Retain appendOrUpdate with matchingColumns=[session_id]. A retry after an ambiguous/transient write outcome must target the same session record rather than append a second lead.

### 5.4 Main-workflow behavior
No main-workflow graph change in Feature 001. Existing AI instruction remains: claim success only if the tool returns success=true. Full deterministic main-flow submission is deferred to 002-deterministic-lead-submission after canonical lead payload state is designed.

## 6. Failure Categories Covered
- validation_failed — existing behavior, unchanged.
- duplicate_conflict — existing behavior, unchanged.
- lookup_failed — new.
- write_failed — new.
- created / updated — existing success behavior, unchanged.

## 7. Static QA
Candidate must pass:
- valid JSON;
- unique node names and IDs;
- no removal/change to existing protected success/validation/conflict nodes;
- success and error branches both connected;
- retry settings present only on the two external Google Sheets operations in scope;
- no embedded credentials/API keys/secrets introduced;
- locked R1 JSON byte/content remains untouched.

## 8. Runtime Test Gate
Focused R2 cases must cover successful create/update, validation failure, duplicate conflict, forced lookup failure, forced write failure, retry recovery, no duplicate after retry, and AI no-false-success behavior. After focused R2 tests, run all permanent R1 10/10 cases.

Runtime evidence must record workflow/subworkflow version, execution ID, timestamp, test session, expected/actual path, tool result, row reference where applicable, and PASS/FAIL.

## 9. Rollback
Rollback unit is the validated handoff subworkflow only. If the candidate fails runtime QA, keep the current published/validated subworkflow unchanged and discard/deactivate the candidate. Never overwrite the R1 locked main workflow.

## 10. Release Gate
Promotion is blocked until:
1. Active n8n main workflow and subworkflow identities are verified in the runtime environment.
2. Candidate import/static validation succeeds.
3. Focused R2 runtime tests pass.
4. R1 10/10 regression passes.
5. No P0/P1 unresolved failure remains.
6. Convergence review confirms implementation matches spec/clarify/plan/tasks.
7. PROJECT_STATE and CHANGELOG are updated with evidence.

## 11. Deferred Feature
002-deterministic-lead-submission will own canonical personal lead state and removal of the final write decision from AI tool choice. It must not be mixed into this bounded R2 error-handling candidate.
