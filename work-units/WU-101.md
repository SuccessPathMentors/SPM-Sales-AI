## Objective
Capture one privacy-minimized, deterministic analytics event per completed customer turn so future optimization can be driven by real traffic without changing the current customer-facing answer or business truth gates.

## Why this unit exists
Phase 2 starts by learning from real customer traffic. The current RC4.3.3 workflow already builds and redacts `SPM_TELEMETRY_V2`, but it does not persist a dedicated business analytics event that contains the full WU-101 signal set.

WU-101 extends the existing observability baseline rather than replacing it.

## Authoritative requirement
The Phase 2 backlog defines WU-101 with:
- goal: capture real customer conversation signals needed for optimization;
- scope: intent, secondary intent, confidence, language, session outcome, source gate, fallback use, clarification use, human-request signal, lead-conversion outcome, and safe telemetry;
- acceptance direction: no secrets/unnecessary PII and no change to customer-facing behavior.

## Design decision proposed for freeze
### Session grouping
Do not hash or persist raw session IDs in analytics.

Use an internal pseudonymous key persisted in existing Redis sales state:
- first turn: `sales_state.analytics.session_key = "conv-" + correlation_id`;
- later turns: preserve the same value through existing non-destructive state merge;
- `sales_state.analytics.turn_index` increments once per customer turn before the existing WU90 Redis save.

This gives stable session grouping without storing raw session IDs in the analytics sink.

### Persistence
Use a dedicated `CONVERSATION_ANALYTICS` tab in the existing runtime workbook for WU-101 V1. This avoids introducing a new infrastructure dependency. It is a Phase-2 design choice, not a historical requirement.

### Customer-path isolation
The analytics write must be dispatched through a dedicated logger path/subworkflow and must fail open. A logging failure must never:
- change the answer;
- change lead truth;
- claim or suppress booking/handoff/payment success;
- block the chat response.

## Scope
### In scope
- Extend the existing redacted telemetry into `SPM_WU101_CONVERSATION_ANALYTICS_V1`.
- Deterministic field mapping only; no second LLM classification.
- Pseudonymous session grouping and turn count.
- STAGING-only analytics logger and Google Sheets append/readback validation.
- Observable but fail-open analytics-write failure.
- Static, contract, runtime and regression evidence.

### Out of scope
- storing raw customer question/message;
- WU-102 unanswered-question queue;
- dashboard/KPI presentation (WU-109);
- KB maintenance automation (WU-103);
- human handoff execution (WU-107);
- WhatsApp staff notification (WU-108);
- scheduling/booking/payment activation;
- direct edit or activation of current Production.

## Signal mapping
- `primary_intent` ← `classification.spm_intent`
- `secondary_intent` ← `classification.secondary_spm_intent`
- `confidence` ← `classification.confidence`
- `language` ← validated classifier language, otherwise safe `language_hint`, otherwise `unknown`
- `journey_stage` ← `journey_decision.stage`
- `source_gate` ← `source_gate_result.gate` or `source_gate_decision.gate`
- `classifier_route` ← existing `classifier_route`
- `clarification_used` ← existing clarification route/flag
- `fallback_used` ← classifier fallback route
- `human_requested` ← primary/secondary `human_handoff` OR existing handoff/support-request state
- `lead_outcome` ← verified WU95 lead result/state only; never inferred from model prose
- `lead_id_present` ← boolean only; actual lead ID is not persisted in WU-101 analytics
- `opt_out` ← `sales_state.nurture.opt_out`
- `action_status` ← existing action result status
- `degraded`, `recovery_mode`, `duration_ms`, `error_codes` ← existing WU97 telemetry

- Any raw PII/message persisted in analytics.
- Any secret/credential value persisted.
- Analytics output used as source of truth for lead/booking/handoff/payment success.
