# WU-102 — Unanswered Question Queue

Status: SPEC_FROZEN — READY_FOR_IMPLEMENTATION
Version: 1.0
Issue: #25

## Objective
Capture one privacy-safe review-queue record when the current customer turn contains a deterministic unanswered/gap signal, without changing the customer-facing answer or any business truth gate.

## Authoritative requirement
The approved Phase 2 backlog defines WU-102 as an Unanswered Question Queue.

Source trigger candidates:
- no KB match;
- low confidence;
- ambiguous intent;
- fallback used;
- repeated question;
- customer says they did not understand;
- human requested;
- unsupported / out-of-scope question;
- poor-answer feedback.

Source minimum fields:
- timestamp;
- session_id;
- raw question or safely redacted question;
- language / dialect hint;
- predicted intent;
- confidence;
- KB-match status;
- fallback flag;
- human-request flag;
- repeat flag;
- resolution status;
- approved-answer status;
- added-to-KB status.

The source calls these trigger candidates, not mandatory V1 triggers. Freeze review therefore keeps only signals that already exist deterministically in the current runtime.

## Freeze review findings
### Signals already deterministic in runtime
1. **No approved static evidence**
   - WU91 exposes `source_gate_decision.evidence_count`, `source_refs`, `reason_code` and retrieval statuses including `NO_MATCHING_ACTIVE_EVIDENCE` / `NO_AUTHORIZED_STATIC_SOURCE`.
   - V1 queues this only for a static-answer-eligible turn. A missing live adapter or an intentionally excluded live action is not automatically treated as a KB gap.

2. **Low confidence / fallback**
   - WU88 routes an invalid intent or confidence `< 0.60` to `classifier_route='fallback'`.

3. **Ambiguous / below threshold**
   - WU88 routes `classification.ambiguous=true` or confidence below the intent threshold to `classifier_route='clarify'`.

4. **Fallback used**
   - Existing `classifier_route='fallback'` is directly observable.

5. **Human requested**
   - Reuse the WU-101 deterministic mapping: primary/secondary `human_handoff`, WU95 handoff contract request, or persisted support handoff-request state.
   - This records a request only; it MUST NOT claim handoff execution succeeded.

6. **Unsupported / out-of-scope**
   - `classification.spm_intent='out_of_scope'` is a deterministic classifier output and is eligible for queue review.

### Deferred from V1 because no dedicated deterministic runtime signal exists
- repeated question;
- explicit “I did not understand” feedback;
- poor-answer feedback.

These remain approved backlog candidates, but WU-102 V1 MUST NOT infer them with a second LLM or silently map every complaint to poor-answer feedback. They require a later explicit signal/change request before certification.

## Frozen V1 trigger reasons
A qualifying turn creates **one** queue record with one or more reasons from this allowlist:

- `NO_STATIC_EVIDENCE`
- `LOW_CONFIDENCE_FALLBACK`
- `AMBIGUOUS_OR_BELOW_THRESHOLD`
- `FALLBACK_USED`
- `HUMAN_REQUESTED`
- `OUT_OF_SCOPE`

Multiple reasons on one turn MUST NOT create duplicate rows.

## Frozen qualification rules
`queue_required=true` when at least one frozen V1 trigger reason is present.

Deterministic mapping:
- `NO_STATIC_EVIDENCE` ← static-answer-eligible source plan/decision with `evidence_count=0` and a no-authorized/static-evidence reason.
- `LOW_CONFIDENCE_FALLBACK` ← `classifier_route='fallback'` with numeric confidence `< 0.60` or invalid-classifier fallback evidence.
- `AMBIGUOUS_OR_BELOW_THRESHOLD` ← `classifier_route='clarify'` OR `classification.ambiguous=true` OR numeric confidence below validated classifier threshold.
- `FALLBACK_USED` ← `classifier_route='fallback'`.
- `HUMAN_REQUESTED` ← existing deterministic WU-101 handoff-request mapping.
- `OUT_OF_SCOPE` ← primary or secondary intent equals `out_of_scope`.

A normal confident direct answer with approved evidence MUST produce `queue_required=false` and no queue write.

## Privacy decision for question capture
WU-102 is the first work unit allowed to persist question text, so V1 uses a strict **redact-or-withhold** policy.

1. The raw customer message may be read transiently by the WU-102 builder but MUST NOT be persisted.
2. Build `redacted_question` deterministically by:
   - scrubbing email and phone patterns;
   - replacing explicit WU89 PII/contact entity values (including parent/student names and contact identifiers) with typed redaction tokens;
   - applying spreadsheet/formula-injection escaping at the adapter boundary.
3. If WU89 reports PII but the builder cannot prove the detected value was removed, set:
   - `question_capture_status='WITHHELD_PII_RISK'`
   - `redacted_question=null`
4. Otherwise set:
   - `question_capture_status='STORED_REDACTED'`
5. No second LLM may be used for redaction or queue qualification.

This deliberately favors losing question text over persisting uncertain PII.

## Identifier and dedupe design
- `queue_session_key` reuses the internally generated WU-101 `analytics_session_key`; raw n8n/chat session ID is forbidden.
- `turn_index` reuses WU-101 durable turn index.
- `queue_event_id = uq-<queue_session_key suffix>-<turn_index>` or another deterministic equivalent derived only from the internal session key + turn index.
- Google Sheets sink uses `queue_event_id` as the matching/idempotency key so re-execution of the same turn updates/no-ops rather than appending a duplicate row.

- `approved_answer_status='NOT_REVIEWED'`

WU-102 does not approve answers or write knowledge. Those lifecycle values exist for human review and downstream WU-103 consumption only.

## Persistence decision
WU-102 V1 uses a dedicated `WU102_UNANSWERED_STAGING` tab in the existing SPM runtime workbook for STAGING certification.

The queue is operational review data. It MUST NOT be loaded into the Sales Agent prompt and MUST NOT become an automatic knowledge source.

## Customer-path isolation
Queue logging is secondary observability/review infrastructure and MUST be fail-open:
- queue write failure must not alter the answer;
- queue write failure must not alter lead truth;
- queue write failure must not alter booking/handoff/payment truth;
- queue write failure must not block the chat response;
- retry of queue logging must never repeat business writes.
