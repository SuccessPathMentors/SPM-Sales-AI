# WU-104 — Short Query & Ambiguity UX

Status: SPEC_FROZEN — READY_FOR_IMPLEMENTATION
Version: 1.0
Issue: #48

## Objective
Make short customer messages feel natural and context-aware without treating shortness as ambiguity, without copying stale context, without re-asking known information, and without allowing an unresolved ambiguous turn to trigger an irreversible/business action.

## Freeze review — current runtime reality
The current runtime already contains important behavior that WU-104 must preserve:

1. The semantic classifier may use PREVIOUS SALES STATE for short replies, yes/no answers, corrections, an awaiting entity, known grade/subject/student, prior question and current journey stage.
2. The classifier is explicitly told not to copy an unrelated old intent and not to invent unstated facts.
3. Genuine uncertainty routes to `classifier_route='clarify'` with `classifier_safe_action='ASK_ONE_CLARIFYING_QUESTION'`.
4. Journey state already exposes the ask policy:
   - `ask_only_smallest_relevant_missing_field` when something relevant is missing;
   - `do_not_reask_known_fields` otherwise.
5. Registration consent/final confirmation already has a deterministic context-bound guard: generic Yes/OK is accepted only while the active registration flow is explicitly awaiting confirmation/consent.
6. `out_of_scope` is already required to remain strict and must not be used merely because wording is short, informal, typo-heavy, dialectal or uncertain.

WU-104 therefore hardens and tests short-query/context behavior around the existing classifier; it does not replace the classifier or business gates.

## Material freeze decisions

### 1. Shortness is a feature, not a decision
A message may be tagged as short for routing/telemetry purposes, but `short_query_detected=true` MUST NOT by itself:
- set `ambiguous=true`;
- lower confidence;
- force clarification;
- force fallback;
- change intent;
- change source/business/action eligibility.

V1 short-message feature detection is bounded and deterministic:
- normalized visible text length <= 48 characters; AND
- lexical token count <= 5.

The feature detector is Unicode-safe and must not reject Arabic/French punctuation or code-switching.

### 2. Current explicit meaning has precedence over old context
A clear current semantic request such as `price?`, `how much?`, `refund?`, `human?`, or their EN/AR/FR equivalents may remain direct when the existing classifier produces a valid high-confidence, non-ambiguous intent.

Previous state must not change a clear current support/payment/pricing/policy/etc. request into the previous sales intent.

### 3. Bare entity fragments are different from explicit semantic requests
The following short forms are considered context-sensitive fragments rather than complete business requests when they do not contain explicit semantic request language:
- grade-only (`Grade 10`, `10th`, Arabic/French grade equivalent);
- subject-only (`Math`, `Physics`, etc.);
- location-only (`Toronto`, etc.);
- day/date-only (`Saturday`, `tomorrow`, etc.);
- time-only (`6 PM`, `18:00`);
- generic affirmation/negation (`yes`, `no`, `ok`, EN/AR/FR equivalents).

A bare fragment may bind automatically only when one compatible awaited meaning is deterministically established.

### 4. Deterministic context binding requires exactly one compatible target
A fragment may be marked `BOUND_DETERMINISTIC` only when all are true:
- a usable current journey/conversion state exists;
- exactly one compatible `awaited_entity` / awaiting field is active;
- the fragment structurally matches that expected type;
- no clear current semantic intent conflicts with the binding;
- the binding would not itself authorize an irreversible action.

If zero compatible targets exist, or two or more meanings remain plausible, the fragment is `NEEDS_CLARIFICATION` or `UNSAFE_TO_BIND`.

No fuzzy historical-intent copying is allowed.

### 5. Awaited-entity compatibility map
V1 supports deterministic compatibility only for these bounded categories:
- grade fragment -> grade/grade_level awaiting field;
- subject fragment -> subject awaiting field;
- location fragment -> city/location awaiting field;
- day/date fragment -> scheduling day/date awaiting field;
- time fragment -> scheduling time/time_window awaiting field;
- generic Yes/No -> only an already-authorized deterministic yes/no context.

Registration confirmation/consent remains governed by the existing locked confirmation-stage guard; WU-104 does not create a second confirmation mechanism.

Unknown/custom awaiting fields are not auto-bound by WU-104 V1.

### 6. Corrections override binding
Explicit correction language in the current turn has precedence over an awaited slot or old state. WU-104 must not transform a correction into a generic slot reply.

Examples:
- `Actually Grade 11` must not preserve old Grade 10.
- `No, Physics` must not bind blindly as an affirmation/negation when the semantic correction is subject-related.

### 7. One-question clarification contract
When clarification is required, the customer-facing turn must:
- ask exactly one question;
- be concise;
- ask only the smallest relevant distinction needed to continue;
- not ask for information already known in state;
- avoid a multi-field form/list;
- use the current/dominant language (`en|ar|fr`);
- never claim a booking/payment/registration/handoff action succeeded;
- never execute an irreversible/business write.

Examples of acceptable clarification shape:
- EN: `Are you asking whether we offer Math, or are you looking for Math tutoring for a student?`
- AR: `هل تسأل إذا كنا ندرّس الرياضيات، أم أنك تبحث عن دروس رياضيات لطالب؟`
- FR: `Demandez-vous si nous proposons les mathématiques, ou cherchez-vous du tutorat en mathématiques pour un élève ?`

The exact wording may vary, but the business distinction and one-question limit are contractual.

### 8. Clarification loop cap
WU-104 introduces additive safe state under `sales_state.clarification`:
- `active` boolean;
- `clarification_key` non-customer deterministic key;
- `attempt` integer 0..2;
- `reason_code` enum/code;
- `language` (`en|ar|fr`);
- `expected_response_type` safe categorical value;
- `last_intent` optional existing intent name;
- `updated_at` timestamp.

Forbidden in this state:
- raw customer text;
- raw session ID/correlation ID;
- phone/email/name/contact data;
- secret/token/credential values.

Rules:
- first unresolved ambiguity for key -> attempt 1, ask one clarifying question;
- second consecutive unresolved ambiguity for same key -> attempt 2, ask one final compact clarification if it materially differs and can resolve the ambiguity;
- another unresolved turn for the same key must not ask the same question again; use `SAFE_FALLBACK_OR_HUMAN_HELP` and reset/close the active loop;
- a resolved/direct turn resets clarification state;
- a clearly different current intent resets the old ambiguity key;
- changing language does not create an unlimited new loop for the same business ambiguity.

### 9. No second LLM decision layer
WU-104 may improve the existing classifier prompt/context and add deterministic pre/post guards, but it MUST NOT introduce a second LLM whose purpose is to re-classify whether the first classifier was correct or whether clarification is required.

Ambiguity routing must remain traceable to:
- existing classifier output;
- deterministic short-query features;
- deterministic context-binding rules;
- deterministic clarification-attempt state.

### 10. Existing action gates remain authoritative
WU-104 does not grant action permission.

When `clarification_required=true`:
- `irreversible_action_allowed=false`;
- action gateway execution remains blocked;
- registration/payment/booking/handoff success cannot be inferred;
- source/business truth is unchanged.

## Precedence order
For one customer turn, WU-104 applies this order:

1. current explicit correction / clear semantic meaning;
2. locked registration confirmation/consent guard when its exact state prerequisites are satisfied;
3. deterministic awaited-entity binding for a structurally compatible bare fragment;
4. valid existing classifier direct route when no WU-104 safety condition contradicts it;
5. one-question clarification when genuine ambiguity remains;
6. loop-capped safe fallback/human-help option after repeated unresolved ambiguity.

Old/stale context never outranks a clear current message.

## Required STAGING runtime matrix
### A. Clear short semantics — fresh session
- EN `price?` -> pricing/direct.
- AR `السعر؟` -> pricing/direct.
- FR `prix ?` -> pricing/direct.
- EN/AR/FR explicit human-agent short request -> human_handoff/direct.
- explicit short refund request -> refund_policy/direct.

### B. Bare fragments — no usable context
- `Math` / Arabic/French equivalent -> no invented student goal/action; clarify when multiple meanings remain.
- `Grade 10` -> no stale binding; clarify when context is absent.
- `Saturday` -> no invented booking; clarify when context is absent.
- `6 PM` -> no invented booking; clarify when context is absent.
- generic `yes` / `no` -> no business action in a fresh session.

### C. Context-bound fragments
- awaiting grade + `Grade 10` -> bound deterministically.
- awaiting subject + `Math` -> bound deterministically.
- awaiting city/location + `Toronto` -> bound deterministically.
- awaiting scheduling day/date + `Saturday` -> bound deterministically.
- awaiting scheduling time + `6 PM` -> bound deterministically.

### D. Corrections and stale context
- prior Grade 10 + `Actually Grade 11` -> current correction wins.
- awaiting grade + explicit `price?` -> pricing direct; do not consume as grade.
- stale pricing intent + `I can't log in` -> account_login/support priority.

### E. Clarification loop
- first ambiguous turn -> attempt 1, one question.
- second unresolved same key -> attempt 2, no duplicate wording/meaning loop.
- third unresolved same key -> safe fallback/human-help option, no third repeat.
- direct resolution after clarification -> state reset.

### F. EN/AR/FR parity
Equivalent ambiguity/context scenarios produce equivalent business routing while response text stays in the matching language.
