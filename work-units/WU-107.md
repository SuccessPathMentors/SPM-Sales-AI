# WU-107 — Human Handoff Execution

Status: SPEC_FROZEN_FOR_DESIGN
Issue: #67
Upstream: WU-106 LOCKED
Phase: 2

## 1. Objective
Implement verifiable human-handoff execution on top of the locked WU-106 conversation stack. WU-107 converts a preserved `human_handoff` request into a downstream handoff transaction with explicit truth states, idempotency, retry/failure behavior, privacy controls, and customer-facing action honesty.

WU-107 does **not** redefine intent classification, tutoring sales logic, WhatsApp staff notification (WU-108), dashboards/KPIs (WU-109), or Production release authority.

## 2. Locked upstream invariants
WU-107 inherits and must not weaken:
- WU-104 ambiguity/correction/action-safety controls;
- WU-105 Golden Intent behavior;
- WU-106 multi-turn context, support interruption, and action-honesty behavior;
- the authoritative 62-intent taxonomy;
- WU-101/WU-102 analytics/queue isolation semantics;
- Production hard-stop.

## 3. Handoff truth-state contract
Canonical WU-107 handoff states:

`NONE -> REQUESTED -> QUEUED -> ACCEPTED | FAILED | CANCELLED`

Definitions:
- `NONE`: no active handoff request.
- `REQUESTED`: customer/support flow explicitly requested a human; no downstream receipt yet.
- `QUEUED`: downstream handoff destination durably accepted the request into its queue; no human acceptance is proven yet.
- `ACCEPTED`: authoritative downstream evidence proves a human/support assignee accepted the case.
- `FAILED`: handoff execution could not be completed after bounded retry or permanent downstream failure.
- `CANCELLED`: request was explicitly cancelled before acceptance where cancellation is supported.

Truth rules:
- `REQUESTED` must never render as `a human has received your case`.
- `QUEUED` may render only as `your request has been placed in the support queue` or equivalent, if queue receipt is verified.
- `ACCEPTED` language requires authoritative downstream acceptance evidence.
- classifier intent, generated text, or local optimistic state cannot create `QUEUED` or `ACCEPTED` truth.
- no invented staff name, case ID, queue position, ETA, or acceptance timestamp.

## 4. Handoff request contract
Minimum internal request envelope:
- `handoff_schema`
- `handoff_event_id`
- `created_at`
- `workflow_release`
- `channel`
- `handoff_session_key` (pseudonymous where possible)
- `correlation_id`
- `reason_code`
- `source_intent`
- `source_stage`
- `priority`
- `requested_language`
- `customer_context_summary` (bounded/redacted)
- `support_context_flags`
- `handoff_state`
- `attempt_count`
- `idempotency_key`
- `downstream_receipt_present`
- `downstream_acceptance_present`
- `pii_policy_version`

Raw unrestricted conversation history is not part of the default WU-107 handoff envelope.

## 5. Reason-code allowlist
Initial deterministic reason codes:
- `EXPLICIT_HUMAN_REQUEST`
- `TECHNICAL_SUPPORT`
- `COMPLAINT_ESCALATION`
- `REPEATED_FAILURE_OR_LOOP`
- `OUT_OF_SCOPE_SUPPORT`
- `ACCOUNT_OR_CONTACT_SENSITIVE_CHANGE`
- `OTHER_APPROVED_HANDOFF`

The reason code must be derived from existing locked runtime signals/intent/state, not from a second WU-107 LLM.

## 6. Destination abstraction
WU-107 owns a generic handoff execution interface, not a WU-108 WhatsApp notification channel.

Required provider contract:
- accepts one idempotency key;
- returns structured `accepted_for_queue` / `failed` result;
- optionally returns a non-secret downstream receipt/reference;
- cannot silently turn a queue receipt into human acceptance;
- supports bounded retry classification (`transient` vs `permanent`) where possible.

The specific staff-notification channel is downstream scope and must not be coupled into WU-107 core truth semantics.

## 7. Idempotency and retry
- one deterministic idempotency key per logical handoff request;
- duplicate workflow execution or retry must not create duplicate downstream cases;
- bounded retry only for retryable downstream failures;
- retry attempt count must be observable;
- retry exhaustion yields `FAILED`, never fake success;
- customer chat response must remain truthful if the handoff sink fails.

## 8. Conversation-state behavior
- explicit handoff/support request suspends the active sales objective;
- known useful context may be summarized for support within privacy limits;
- sales must not auto-resume after `REQUESTED/QUEUED/ACCEPTED` unless the customer explicitly resumes a sales topic;
- handoff failure must not erase the customer request or corrupt registration/scheduling state;
- a current opt-out/privacy/safety instruction has higher priority than sales continuation.

## 9. Privacy / security
Default WU-107 envelope must exclude:
- passwords, tokens, credentials, API keys;
- unrestricted raw conversation dump;
- payment/card/banking data;
- unnecessary student/parent PII;
- raw session IDs when a pseudonymous key is sufficient.

Any contact data required for an actual support callback must come from an already-authorized canonical customer/contact source and be purpose-limited to the handoff transaction.

## 10. Deterministic acceptance matrix
At minimum WU-107 must cover:
1. explicit `I want to speak with a person`;
2. technical-support interruption;
3. complaint escalation;
4. duplicate retry/idempotency;
5. transient downstream failure then success;
6. permanent downstream failure;
7. queue receipt without human acceptance;
8. verified human acceptance;
9. stale sales context after handoff;
10. explicit customer resume to sales after handoff;
11. EN/AR/FR handoff request parity;
12. privacy/secret negative cases;
13. no fake case/staff/ETA metadata;
14. WU-106 12-journey regression compatibility.

## 11. Acceptance criteria
- AC-01 Explicit human request creates exactly one logical handoff request.
- AC-02 Support/complaint escalation can initiate the same handoff contract without restarting sales.
- AC-03 `REQUESTED`, `QUEUED`, and `ACCEPTED` are materially distinct truth states.
- AC-04 No customer-facing human-received/accepted claim occurs before authoritative acceptance evidence.
- AC-05 Duplicate execution is idempotent.
- AC-06 Transient retry cannot create duplicate cases.
- AC-07 Permanent failure is represented honestly and remains observable.
- AC-08 Handoff failure does not alter unrelated sales/registration truth.
- AC-09 Raw secrets/unnecessary PII are absent from handoff telemetry/payload by default.
- AC-10 EN/AR/FR equivalent handoff signals follow the same truth model.
- AC-11 Existing WU-106 support interruption behavior remains compatible.
- AC-12 Production remains untouched unless separately approved.

## 12. Implementation stages
1. Scope / truth-state freeze — COMPLETE by this spec.
2. Provider-neutral request schema + state transition validator.
3. Idempotency/retry/privacy deterministic contract tests.
4. Exact WU-106 locked-lineage candidate build.
5. Inactive isolated STAGING handoff sink/provider simulator.
6. Success/failure/duplicate runtime certification.
7. Owner-observed Test Chat certification.
8. Full WU-106 regression.
9. Material review.
10. Explicit Owner approval and LOCK.

## 13. Hard stops
- direct Production mutation;
- optimistic `ACCEPTED` state;
- duplicate downstream case creation;
- unrestricted raw chat export;
- fake human/staff/case/ETA metadata;
- WU-108 notification-channel coupling inside WU-107 truth contract;
- self-approval or self-lock.

## 14. Exit
WU-107 may return only `READY_FOR_REVIEW` or `BLOCKED`. Final lock requires explicit Owner approval.
