# CR-103-02 — Bind Regression PASS to Tested Candidate Payload

Status: APPROVED FOR WU-103 IMPLEMENTATION BRANCH
Parent: WU-103 Knowledge Maintenance Loop
Issue: #30

## Problem
The frozen WU-103 ledger stored `regression_status` and `regression_evidence_sha256`, but did not persist which exact candidate payload hash the regression evidence tested.

Without an explicit stored binding, a candidate could be edited after a PASS and the publisher could not deterministically prove that the PASS still applies to the current payload.

## Change
Add required ledger field:

`regression_payload_sha256`

Allowed value: null before/without a bound regression run, or a lowercase SHA-256 string when regression evidence exists.

## Gate
STAGING publication requires all existing gates plus:

`regression_status == PASS`

and

`regression_payload_sha256 == candidate_payload_sha256`

Any candidate payload edit changes `candidate_payload_sha256`; prior regression evidence is therefore invalid for publish until regression is rerun and the new hash is recorded.

## Scope
- strict contract update;
- deterministic core gate update;
- CI tests;
- STAGING ledger header update;
- future n8n maintenance/publisher workflow reads this field.

## Non-scope
- no Production KB write;
- no relaxation of human approval/release approval;
- no automatic approval or automatic regression PASS;
- no customer/runtime PII added.

## Safety result
This change closes a release-integrity gap and makes the regression evidence cryptographically bound to the exact knowledge payload being published.
