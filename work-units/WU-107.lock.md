## Locked WU-107 objective
WU-107 locks deterministic, verifiable human-handoff execution on top of the formally locked WU-106 conversation stack.

The locked implementation:
- creates a durable handoff queue record only from approved current-turn handoff/support signals;
- keeps REQUESTED, QUEUED, ACCEPTED, FAILED, and CANCELLED materially distinct;
- allows QUEUED only with durable queue receipt/tool evidence;
- allows ACCEPTED only with durable queue receipt plus authoritative downstream human-acceptance evidence;
- prevents classifier labels, generated text, or persisted labels alone from creating execution truth;
- enforces idempotent repeat behavior and avoids duplicate tool writes for an existing queued handoff;
- uses bounded Redis retry/failure behavior;
- preserves request truth under load/save failure without falsely claiming queue or human acceptance;
- minimizes handoff payload PII and excludes unrestricted raw chat, raw session identity, secrets, credentials, and unnecessary contact values;
- allows support/complaint/human-request flows to interrupt sales without auto-resuming sales;
- preserves WU-106 locked behavior and the authoritative intent taxonomy;
- keeps WU-108 WhatsApp staff notification out of WU-107 scope;
- keeps Production protected.

## Locked truth-state contract
Canonical states:

`NONE -> REQUESTED -> QUEUED -> ACCEPTED | FAILED | CANCELLED`

Evidence rules:
- REQUESTED: customer/support flow requested a human; no downstream receipt required.
- QUEUED: durable queue receipt/tool evidence is required.
- ACCEPTED: durable queue receipt plus authoritative downstream human-acceptance evidence is required.
- FAILED: queue/acceptance success is not claimed.
- CANCELLED: request was explicitly cancelled where supported.

A persisted `ACCEPTED` label is not trusted by itself. If human-acceptance evidence is absent but a durable queue receipt remains verified, the strongest valid truth is QUEUED. Unsupported success labels fail closed.
