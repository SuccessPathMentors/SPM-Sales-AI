# WU-103 — Knowledge Maintenance Loop

Status: SPEC_FROZEN — READY_FOR_IMPLEMENTATION
Version: 1.0
Issue: #30

## Objective
Convert locked WU-102 gap evidence into human-approved, versioned knowledge-change candidates with deterministic regression and release gates, without allowing queue data, an AI agent, or a failed/stale test path to become production knowledge automatically.

## Authoritative requirement
Phase 2 defines the loop as:

`Real traffic → detect gap → unanswered queue → human review → approve/edit answer → map to intent/source → add/update KB → regression test → publish → measure again`

Hard rule: no answer becomes production knowledge without review/approval and regression evidence.

## Freeze review — current KB reality
The current canonical KB is legacy and does **not** expose one common version column.

Observed source-family identifiers:
- `PACKAGES` → `record_id`
- `POLICIES` → `record_id`
- `SUBJECTS` → `record_id`
- `SUBJECT_PATHWAYS` → `pathway_id`
- `FAQ` → `record_id`
- `SERVICES` → `service_id`
- `LOCATIONS` → `record_id`
- `FALLBACKS` → `record_id`

WU91 already resolves source evidence using the compatible identifier fallback order `record_id | service_id | pathway_id | rule_id | id` and reads ACTIVE rows only.

Current canonical records mainly use:
- a family-specific ID;
- source-family payload fields;
- `status=ACTIVE`;
- optional `last_reviewed` / source URL fields.

Therefore WU-103 MUST NOT pretend current records already have a version number and MUST NOT destructively overwrite a legacy ACTIVE row during certification.

## Material freeze-review corrections
### 1. Legacy records begin as `LEGACY_UNVERSIONED`
For the first WU-103-managed UPDATE of an existing canonical record:
- `base_revision='LEGACY_UNVERSIONED'`;
- capture the exact canonical target row;
- calculate `base_fingerprint_sha256` over the normalized authoritative row fields;
- the first WU-103-managed candidate becomes `candidate_revision='v1'`.

Subsequent approved revisions increment only inside the WU-103 lineage (`v2`, `v3`, ...).

This avoids inventing a historical version that did not exist.

### 2. Optimistic concurrency is mandatory
An UPDATE is publish-eligible only when a fresh read of the target record produces the same `base_fingerprint_sha256` captured at candidate creation.

If the target changed, publishing stops with `STALE_BASE_RECORD`; the operator must create/rebase a new change candidate. No last-write-wins behavior is allowed.

### 3. Business truth is not ordinary FAQ maintenance
`PACKAGES` and `POLICIES` contain pricing/policy truth. A customer gap is not evidence that a new price, discount, policy, cancellation rule, or refund rule is true.

Changes targeting `PACKAGES` or `POLICIES` require:
- `business_truth_approval=true`;
- a deterministic approved source reference, normally an `OWNER_DECISION` or other separately approved authoritative business source;
- human approval of the exact candidate payload.

Without this gate the candidate may be logged/reviewed but MUST NOT advance to test/publish eligibility.

### 4. Queue text is evidence, not knowledge
WU-102 `redacted_question` may inform review but MUST NOT be copied automatically into an approved KB answer. The final candidate payload is a curated human-approved knowledge artifact.

### 5. No AI self-approval
An AI agent may suggest/draft candidate text or mappings, but automation MUST NOT write or transition the authoritative human-approval fields.

## Family adapter contract
Each family has an exact ID field and an allowlisted payload schema derived from the existing canonical sheet headers. The implementation MUST reject unknown properties instead of forwarding arbitrary JSON to Google Sheets.

Minimum ID-field map:
- FAQ → `record_id`
- SUBJECTS → `record_id`
- SUBJECT_PATHWAYS → `pathway_id`
- SERVICES → `service_id`
- LOCATIONS → `record_id`
- FALLBACKS → `record_id`
- PACKAGES → `record_id`
- POLICIES → `record_id`

For UPDATE, `target_record_id` is mandatory and must resolve to exactly one canonical ACTIVE row in the selected family.

For ADD, `target_record_id` is null until a deterministic, collision-checked family-compatible ID is allocated by the publish adapter. No fuzzy name/topic match may choose the ID.

## Frozen lifecycle
WU-103 uses a separate maintenance lifecycle. WU-102 queue rows remain provenance evidence and are not the authoritative maintenance-state machine.

Allowed states:
1. `DRAFT`
2. `HUMAN_APPROVED`
3. `TEST_PASSED`
4. `RELEASE_APPROVED`
5. `PUBLISHED`

Side/terminal states:
- `REJECTED`
- `SUPERSEDED`
- `BLOCKED`

Allowed forward path:
`DRAFT → HUMAN_APPROVED → TEST_PASSED → RELEASE_APPROVED → PUBLISHED`

Rules:
- no state may skip directly from DRAFT to TEST_PASSED/RELEASE_APPROVED/PUBLISHED;
- `HUMAN_APPROVED` must be externally/human supplied, not generated by the worker;
- `TEST_PASSED` requires machine-verifiable regression evidence;
- `RELEASE_APPROVED` requires an explicit owner/operator release action after test evidence exists;
- `PUBLISHED` requires successful tool write/readback evidence;
- failed/stale publish attempts remain non-PUBLISHED and leave current canonical truth unchanged.

## Candidate creation rules
A WU-102 queue event may produce at most one non-superseded active WU-103 candidate for the same maintenance purpose.

Candidate creation requires:
- valid WU-102 `queue_event_id` provenance;
- no raw session/contact provenance copied;
- explicit target family;
- explicit ADD or UPDATE;
- human-curated or human-confirmed candidate payload before HUMAN_APPROVED;
- explicit source reference;
- intent mapping when applicable.

Duplicate invocation with the same deterministic candidate key updates/no-ops rather than creating duplicate active candidates.

## Human approval boundary
Automation may populate draft fields and evidence but MUST NOT authoritatively set:
- `review_decision=APPROVED`;
- `change_state=HUMAN_APPROVED`;
- `business_truth_approval=true`;
- `release_approval_status=APPROVED`.

Tests must prove no implementation worker path writes these fields automatically.

## Regression gate
A candidate cannot advance from HUMAN_APPROVED to TEST_PASSED until a deterministic regression pack passes.

Minimum regression evidence:
- one positive case proving the new/updated knowledge answers the originating gap;
- one negative/neighbor case preventing over-broad matching;
- language parity where the candidate language scope requires it;
- existing RC4.3.3/WU-101/WU-102 business-truth behavior remains unchanged outside the intended knowledge change;
- exact candidate payload hash is recorded with the test result.

Regression evidence must bind to `candidate_payload_sha256`; editing the payload invalidates prior test evidence.

## STAGING publish semantics
During WU-103 certification, `publish_environment='STAGING'` only.

### ADD
- allocate a deterministic collision-checked logical record ID appropriate to the selected family;
- write a new `ACTIVE` revision to `WU103_KB_SHADOW_STAGING`;
- retry using the same change ID must not create a duplicate ACTIVE revision.

### UPDATE
- verify canonical base fingerprint still matches candidate `base_fingerprint_sha256`;
- reject stale base;
- mark the previous shadow revision SUPERSEDED when one exists;
- write the new revision ACTIVE;
- preserve lineage and payload hashes.

No canonical Production sheet is edited during STAGING certification.

## Production publish boundary
WU-103 may define/test the Production-publish contract in dry-run/static form, but Production writes remain disabled during STAGING certification.

A future Production publication of an approved WU-103 change requires all of:
- HUMAN_APPROVED;
- TEST_PASSED bound to current candidate payload hash;
- explicit RELEASE_APPROVED action;
- non-stale exact target for UPDATE;
- authorized business source approval for PACKAGES/POLICIES;
- canonical family adapter validation;
- successful write + readback;
- version-history / supersession audit evidence;
- Production workflow/KB target explicitly allowlisted.

No WU-103 implementation agent may self-authorize this release.

## Provenance and measurement
Every published revision must remain linkable by non-customer identifiers:
`source_queue_event_id → change_id → target_family/logical_record_id → revision → regression evidence → publication evidence`

This lineage supports later measurement without exposing raw session/contact identity. WU-109 owns aggregate KPI/dashboard work.

## Privacy
Forbidden in the ledger/shadow candidate contract:
- raw customer message;
- raw n8n/chat session ID;
- email/phone/contact identifiers copied from queue/session;
- parent/student names copied from runtime context;
- tokens/API keys/credentials/secrets.

WU-102 redacted text may be read for review but the final candidate payload must be independently curated and rechecked for PII.

## Safety / hard stops
- automatic queue-to-KB promotion;
- AI self-approval or self-release approval;
- publish without regression PASS bound to current payload hash;
- publish without explicit release approval;
- fuzzy overwrite / ambiguous record selection;
- stale-base overwrite;
- price/policy truth inferred from customer text;
- destructive deletion of prior revision/history;
- raw session/contact/message/secret persistence;
- WU103 shadow/queue treated as Production knowledge;
- direct Production KB edit during STAGING certification.

## DAG

Worker cannot self-approve, self-release-approve, self-publish to Production, or self-lock.
