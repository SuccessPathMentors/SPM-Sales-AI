# CR-103-02 — Bind Regression PASS to the Tested Payload

Status: ACCEPTED FOR IMPLEMENTATION REVIEW
Parent: WU-103
Issue: #30
Implementation: merged on `main`

## Problem
`regression_evidence_sha256` proves an evidence artifact exists, but without storing the exact candidate payload hash tested by that evidence a later payload edit could incorrectly retain a previously valid PASS.

## Correction
Add `regression_payload_sha256` to the WU-103 change-ledger contract and STAGING ledger tab.

Rules:
- null before regression evidence is produced;
- machine-written only from regression evidence;
- `regression_status=PASS` is publish-valid only when `regression_payload_sha256 == candidate_payload_sha256`;
- `regression_evidence_sha256` must be a valid SHA-256 and at least two unique regression case IDs must be present;
- editing `candidate_payload_json` changes `candidate_payload_sha256`, invalidating the old PASS until regression is rerun;
- the STAGING publisher is fail-closed on a missing/mismatched regression payload hash;
- no Production KB target or customer-facing runtime is changed by this correction.

## Evidence
The current contract contains `regression_payload_sha256`; current core/publisher tests reject payload-hash mismatch, missing regression evidence, and incomplete regression cases. Runtime Test #6 (`chg-wu103-runtime-legacy-004`) stores a bound PASS where `regression_payload_sha256` exactly equals `candidate_payload_sha256` and includes three regression cases before release.
